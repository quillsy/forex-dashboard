# Niche context research cache

`niche_ecb_est.csv` is the unmodified ECB CSV response for `EST.B.EU000A2X2A25.NB` and `.TT` (latest 45 observations per series). Source: ECB statistics. [Series](https://data.ecb.europa.eu/data/datasets/EST) · [reuse policy](https://www.ecb.europa.eu/stats/ecb_statistics/governance_and_quality_framework/html/usage_policy.ga.html). The CSV is not an ECB endorsement of this dashboard. The companion `niche_context.json` records the fetch time, source hash, source metadata, and context-only display selection.

The Statistics Canada data in `niche_context.json` are adapted from *International merchandise trade by province, commodity, and Principal Trading Partners*, table 12-10-0175-01, vector 1567083339, with the reference date and required attribution in each artifact. This does not constitute an endorsement by Statistics Canada of this product. [Open Licence](https://www.statcan.gc.ca/en/terms-conditions/open-licence).

`niche_context_vintages.json` records prospective fetches as losslessly compressed, size-bounded snapshots after this collector begins; it does not reconstruct historical first-release dates. `niche_context_status.json` anchors the journal and records the last attempt. The journal still grows over time and should be monitored before archival rotation is needed. The separate research display hides values when a collection failed, files disagree, or the cache is old. These files do not affect CORE eligibility or signals.

`mof_week.csv` is the current unmodified CP932 CSV from the Japanese Ministry of Finance's [weekly international securities transactions](https://www.mof.go.jp/policy/international_policy/reference/itn_transactions_in_securities/week.csv). `mof_context.json` selects only the latest 52 post-2014 weeks, preserving all 22 numeric source cells and both separate total net-flow values in units of 100 million JPY. Source: Ministry of Finance, Japan. Selection and German description are adaptations by G8 FX Dashboard; no ministry endorsement is implied. [MoF reuse notice](https://www.mof.go.jp/about_mof/notice/index.html) · [Public Data License 1.0, authoritative Japanese original](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/f7fde41d-ffca-4b2a-9b25-94b8a701a037/24afdf33/20240705_resources_data_outline_05.pdf) · [English reference translation](https://www.digital.go.jp/en/resources/open_data/public_data_license_v1.0). The source's period end and update-date header are not first-publication timestamps.

`mof_context_vintages.json` stores prospective, compressed, hash-chained snapshots and changed overlapping weeks only from collector startup. It cannot recreate earlier first releases. `mof_context_status.json` anchors the archive, records collection failures, and gates the separate MoF display. Each due run makes at most one bounded 500 KB GET to the exact MoF URL; redirects and non-200 responses are rejected. The collector waits at least 20 hours after processing a completed success or failure and honors a longer HTTP 429 `Retry-After`. Open attempts never expire automatically. The observed sample is about 256 KB; about 66 MB/year extrapolates only 260 scheduled weekday GETs without extra manual runs, not a hard annual cap or a Git-growth measurement. Status may be committed after unchanged fetches to prove recent collection; archive snapshots are added only when the validated source bytes change. Failures, stale source periods, or inconsistent files hide MoF values without affecting ECB, StatCan, CORE, or signals. Monitor archive growth before rotation is required.

The workflow runs `python collect_mof_context.py --publish` from a clean `main` checkout. It refreshes from `origin/main`, writes a unique `attempt_id` with `status: attempt_started`, and confirms a successful push of that reservation before issuing the GET. Only that same process may execute the request; a new process never resumes a stored reservation. A second commit publishes the final status, `attempt_completed_at`, cooldown and any cache/history changes together. Both pushes are ordinary fast-forward pushes, without force or automatic conflict retries. The existing workflow concurrency group remains in place, and conflicting Git writers also cause push rejection. The collector and display share strict validation of the extended status fields; valid legacy statuses remain readable.

A failed or unconfirmed reservation push prevents the GET. A rejected or interrupted completion leaves the remote reservation open; an accepted completion whose acknowledgement was lost still preserves its final status and cooldown remotely. The failed working copy blocks rather than retrying publication or collection. Fresh runners always validate the refreshed remote state before considering a new attempt. The minimum cooldown starts at processing completion, not request start, and is never shorter than a longer `Retry-After`.

An interrupted `attempt_started` remains blocked with `MOF_PRIOR_ATTEMPT_INCOMPLETE` even beyond `next_allowed_at`, including legacy attempts without an ID. Investigate the attempt ID, workflow logs and any retained completion evidence before an explicitly authorized operator recovery. Preserve the reservation and archive anchors; do not delete status/history or relabel an unknown attempt as a completed failure to bypass the block. There is no automatic unlock command. Running without `--publish` persists only to the supplied local directory and does not provide durability across disposable runners.
